# Syntra repository audit — 20 September 2026

## Outcome and scope

The application has substantial identity, provisioning, governance and service-automation foundations. This audit fixed concrete authentication, scheduler, readiness, dependency, logging and onboarding problems. It does **not** establish production readiness or HelloID feature parity.

Reviewed repository configuration and the principal authentication, scheduling, HR import, provisioning and admin workflows; ran backend and frontend tests, dependency audit, type checking, build and operational shell tests. Production infrastructure and real customer directories were not accessible. Changes are local and uncommitted.

## Fixed in this change

| Finding | Resolution | Evidence |
|---|---|---|
| Expired login lockout retained previous failures and could immediately lock the account again | A failure after lock expiry starts a fresh count | Login-lockout regression |
| Scheduler startup failure left background work unavailable until restart | Serial retries with capped exponential backoff; cleanup of partial starts and cancellation on shutdown | Recovery/lifecycle tests and API scheduler tests |
| HTTP availability concealed an unavailable scheduler | Critical admin incident and `syntra_scheduler_running` metric | Authorized incident lifecycle and metrics tests |
| HR schedule keys contained a colon rejected by pg-boss | Use slash-delimited keys; register HR schedules before verification | Actual pg-boss schedule create/remove integration test and schedule-key tests |
| pg-boss errors could be unhandled events | Install error listener and send errors to application logging | Scheduler lifecycle test |
| First tenant without signing keys could conceal an invalid vault master key on another tenant | Find the first active signing key across tenants for the readiness probe | Multi-tenant readiness regression |
| API/proxy access logs could expose sensitive query parameters | API logs path-only request URLs; nginx access format omits query and referrer | Fastify log regression; nginx source review |
| Nodemailer dependency had four advisories, including one high severity | Upgrade 9.0.5 to 9.1.1 with minimal lockfile changes | Dependency audit reports zero known advisories afterward |
| Services lacked restart policy | `unless-stopped` for PostgreSQL, API, web and TLS proxy | Compose source review; container runtime unavailable |
| Partial onboarding falsely said a saved login did not exist and allowed duplicate creation | Track created login separately from successful link; report saved steps, link records and disable repeat creation | Onboarding component regressions |

The scheduler metric measures successful startup, not complete per-tenant reconciliation or end-to-end connector health. Vault readiness samples a key; it is not an exhaustive vault-integrity scan. Access-log changes do not guarantee redaction in every error log or external proxy.

## Validation evidence and limits

- Targeted backend regression run: **12 files, 122 tests passed** (`test-results/audit-regression.json`). Includes actual PostgreSQL/pg-boss tests.
- Initial frontend run: **88 files, 845 tests passed**. After the onboarding changes, its component suite passed **19 tests**, including both new partial-failure regressions.
- Operational shell checks: **84 updater and 39 backup checks passed**.
- Dependency audit after update: **zero known advisories** (`test-results/dependency-audit-after.json`). This is a point-in-time advisory check, not proof of absence of vulnerabilities.
- Final typecheck, lint and Vite build **passed after the onboarding change**. Vite reported an approximately 522 KB admin chunk; route-level splitting is a performance follow-up. `git diff --check` reported no whitespace errors.
- Broad backend run: **263 files, 4,987 tests; 4,745 passed, 136 failed, 106 skipped**. Twenty-four files failed; one file was skipped. This run was not green. Some source fixes were made while it ran; the targeted regression run verifies those final backend changes separately.
- Missing LDAP/Samba services account for several failed integration suites. Other failures included transaction/pool timing and OIDC 503 responses. OIDC boundary tests passed in the targeted run using one worker and a four-connection pool. A further nine-file recheck was interrupted before a final result and is not counted as passing.
- Tests used disposable local PostgreSQL 16.14 on Windows and Node 24.19. Production/CI use Node 22. Docker's Linux engine was unavailable, so container startup, nginx syntax under its image, TLS deployment and real AD/LDAP/SFTP behavior remain unverified.
- UI review used two independent assessments. One browser surface was unavailable; the other completed read-only inspection against seeded data. The fixture had no configured connectors, so it did not demonstrate a complete joiner/leaver run.

Temporary reports and fixture files are in ignored `test-results/`. They are local evidence, not committed deliverables. No production credentials, accounts or directory records were changed.

At final cleanup, no PostgreSQL process or listeners on the temporary API/database ports (3300/5433) remained. The temporary services are no longer running.

## Remaining issues, in priority order

1. **P1 — Stale preview results.** Business-rules impact and account-profile previews remain visible after draft/person edits. Bind each response to the precise draft/person and target, suppress late responses, and clearly invalidate results on edits. Include tests where edits occur while preview is in flight.
2. **P1 — Employee departure is split across operations.** Person deactivation ends contracts but explicitly leaves sign-in accounts unchanged; account deactivation separately handles directory write-back/session revocation. Build a person-level orchestration view with an explicit effective date, linked accounts, immediate access-block option, delayed retention actions and per-target completion evidence. Never label a person fully offboarded while managed sign-ins remain active or unverified.
3. **P1 — Onboarding lacks durable completion receipts.** The immediate misleading error is fixed, but provisioning results are discarded. `provision-on-create.ts` returns zero both for no actions and planning timeout; a selected newest run is not a durable correlation to the submitted job. Persist operation/job/run identifiers and explicit pending, blocked, applied, failed and no-match results; retry only unfinished steps.
4. **P2 — Queue publication is not atomic with run creation.** HR/directory import paths create a queued run before enqueueing the worker job. A failed enqueue can leave an orphan run. Use a transactional outbox or another atomic publication approach with idempotent reconciliation; test crash boundaries.
5. **P2 — Partial schedule registration needs reconciliation.** Startup recovery handles worker startup failures; per-tenant scheduling errors can still be logged while the worker is considered running. Add periodic idempotent reconciliation and distinguish worker health from missing schedules.
6. **P2 — Provisioning selectors do not scale.** Account preview loads only the first 200 people; users outside that page cannot be selected. Add server-backed search/paging and searchable entitlement selection.
7. **P2 — Validate production connector behavior.** Before a pilot, run the full Node 22/container suite with LDAP, Samba and SFTP, and exercise interrupted joiner/mover/leaver operations, retries, session revocation and restoration from backup in a test directory.

## Recommended implementation sequence

Use [the provisioning usability review](provisioning-usability-2026-09-20.md) as the product backlog. Start with fresh previews and durable per-person operation receipts, then person-scoped offboarding and a guided connector setup checklist. Broader integrations and visual polish should follow a verified employee lifecycle.

## Employee-lifecycle implementation follow-up

All five usability priorities now have working implementations:

- Person provisioning uses durable, tenant-scoped receipts with exact run correlation, per-target status, evidence, retry and links to the exact run. Queue refusal is stored as a failure instead of disappearing.
- Person pages provide a unified offboarding preview, disable linked sign-ins through the existing directory write-back path, revoke sessions, record partial failures, preserve the original departure clock and queue target-system work.
- A guided provisioning setup page connects HR mapping/import evidence to target profile, rules, lifecycle preview and schedule configuration without presenting saved settings as proof of readiness.
- Business-rule and account-profile previews are invalidated on edits and target/person changes; late responses cannot overwrite the current draft. Destructive rule changes require fresh impact evidence.
- An Employee work page lists unresolved onboarding receipts, incomplete departures and failed actions using the same records as its counts.

Validation after integration: **91 frontend files / 872 tests passed**, production web build passed, typecheck and lint passed, new offboarding API tests passed, receipt persistence/retry tests passed, and the provisioning-run suite passed. The existing scheduler suite passed 52 of 53 tests on the first integration run; its only failure was an outdated handler-selection assertion after adding the new queue, and the corrected assertion passed independently.

### What is still needed

1. **Pilot directory validation.** Exercise joiner, mover and leaver paths against a disposable real AD/LDAP environment on Node 22 and the production containers, including unreachable-domain recovery, paired sync and session logout delivery.
2. **One durable onboarding operation for record creation.** Target provisioning is durable now, but person, contract and optional Syntra-login creation still occur as a browser-driven sequence. Partial failure is accurately reported and repeat creation is blocked, but a refresh cannot resume that pre-provision sequence. Move those writes into an idempotent server operation before broad HR-operator use.
3. **Observed-state completion.** A receipt proves the exact plan and apply result. For the strongest “ready for work” claim, wait for paired read-back and compare observed directory state before declaring the target verified.
4. **Persist connection-test evidence.** The setup checklist deliberately reports connection steps as needing review because connection tests are not stored with time, actor and configuration revision. Add that evidence before using the checklist as an activation gate.
5. **Connector and deployment breadth.** The workflow is coherent around the existing target/source capabilities. HelloID-style breadth still requires the systems customers need, a secure remote-agent story for private networks, connector versioning and credential-rotation operations.
6. **Scale and accessibility validation.** Add server-paged employee work/search and searchable entitlement selection for large tenants, then run keyboard, screen-reader, contrast and responsive tests in a live browser. The current work queue is complete for the stated roughly 400-person deployment but loads the unresolved set in one request.
7. **Operations.** Add alerts for receipts stuck in pending/planning, periodic schedule reconciliation, transactional job publication, and dashboard/runbook coverage for restore drills and failed lifecycle work.
